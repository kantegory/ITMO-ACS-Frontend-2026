## 1. Постановка задачи

В рамках лабораторной работы №2 требовалось привязать сайт, свёрстанный
в ЛР1, к внешнему API средствами `fetch`/`axios`/`xhr`, а также
реализовать моковое API средствами JSON-сервера и подключить к нему
авторизацию, как в примерах по теме «Имитация работы с закрытым API».

Выбранный вариант №5 — «Сервис для обмена рецептами и кулинарных блогов» —
включает вход, регистрацию, личный кабинет, поиск с фильтрацией, страницу
рецепта и социальные функции.

В ЛР1 все данные были статическими, а состояние (сессия, лайки, закладки,
подписки, локальные рецепты и комментарии) хранилось в `localStorage`.
В ЛР2 требовалось перенести эти сущности на сервер и организовать
настоящую проверку учётных данных с выдачей токена.

## 2. Краткое резюме выполненной работы

Сайт из ЛР1 переведён на моковый REST API, работающий на
`json-server@0.17.4` с middleware `json-server-auth@2.1.0`.

Что сделано:

- создан сервер `server/index.js`, который одновременно раздаёт API
  и статические файлы фронтенда на `http://localhost:3000`;
- реализованы регистрация и вход с выдачей JWT и bcrypt-хэшированием
  паролей;
- настроены guards `644`: чтение доступно всем, изменение — только
  владельцу записи (поле `userId`);
- все сущности ЛР1 перенесены в `db.json`: `users`, `recipes`, `comments`,
  `likes`, `bookmarks`, `subscriptions`;
- добавлен клиентский слой `api.js` (fetch, JWT, ресурсы API) и кэш
  `store.js` с синхронными селекторами;
- все страницы переведены на асинхронную загрузку через `appReady`;
- фильтрация и сортировка рецептов выполняются на сервере через
  query-параметры `json-server`, с debounce и отменой устаревших запросов;
- лайки, закладки, подписки, комментарии, создание рецепта и редактирование
  профиля работают через API;
- добавлены состояния загрузки, сообщения об ошибках и баннер недоступного
  API;
- подготовлены `npm run smoke` (9 проверок API) и сценарии ручной проверки.

## 3. Используемый стек и обоснование выбора

| Компонент | Версия | Зачем |
|---|---|---|
| `json-server` | `0.17.4` | Моковый REST API поверх `db.json`, фильтры и сортировка «из коробки» |
| `json-server-auth` | `2.1.0` | JWT, bcrypt, готовые `/register` и `/login`, guards |
| `fetch` | встроенный | HTTP-запросы без дополнительных зависимостей |
| Bootstrap | `5.3.8` | Вёрстка и модальные окна (без изменений с ЛР1) |
| Node.js | 24 | Запуск мокового сервера и скриптов проверки |

Версии `json-server` и `json-server-auth` зафиксированы **без символа `^`**.
Причина: latest-версия `json-server` — `1.0.0-beta.15`, а
`json-server-auth@2.1.0` совместим с веткой `0.17.x`. Установка
`json-server` по умолчанию привела бы к неработающей авторизации.

`axios` сознательно не подключался: в ЛР2 достаточно нативного `fetch`,
а появление `axios` запланировано в ЛР3 при переходе на Vue.

## 4. Архитектура приложения

```
Браузер
  │  fetch + Authorization: Bearer <JWT>
  ▼
server/index.js
  ├── json-server-auth  → /register, /login, guards
  ├── express.static    → HTML, CSS, JS, изображения
  └── json-server router
        │
        ▼
     db.json
```

Сервер и статика работают на одном origin (`http://localhost:3000`).
Это даёт два преимущества:

1. не нужен CORS при штатном запуске;
2. `localStorage`/`sessionStorage` привязаны к тому же origin, что и API.

При запуске фронтенда через другой сервер (например, `python3 -m http.server
8000`) клиент обращается к `http://localhost:3000`; CORS у `json-server`
включён по умолчанию.

Ключевые решения в `server/index.js`:

```js
const app = jsonServer.create();
const router = jsonServer.router(DB_FILE);

// json-server-auth проверяет владение по полю userId,
// поэтому middleware нужен доступ к базе.
app.db = router.db;

app.use(jsonServer.defaults({ static: ROOT }));
app.use(auth.rewriter({
  users: 644,
  recipes: 644,
  comments: 644,
  likes: 644,
  bookmarks: 644,
  subscriptions: 644,
}));
app.use(auth);
app.use(router);
```

Дополнительно `router.render` переопределён так, чтобы из ответов
рекурсивно удалялось поле `password` (bcrypt-хэш не должен попадать
в браузер).

## 5. Модель данных

| Коллекция | Поля |
|---|---|
| `users` | `id`, `email`, `password` (bcrypt), `name`, `bio`, `subscribers` |
| `recipes` | `id`, `userId`, `title`, `dishType`, `difficulty`, `timeMinutes`, `servings`, `description`, `ingredients[]`, `steps[]`, `image`, `likes`, `videoUrl`, `createdAt` |
| `comments` | `id`, `recipeId`, `userId`, `text`, `createdAt` |
| `likes` | `id`, `userId`, `recipeId` |
| `bookmarks` | `id`, `userId`, `recipeId` |
| `subscriptions` | `id`, `userId`, `authorId` |

В ЛР1 в рецептах и комментариях использовалось поле `authorId`.
В ЛР2 оно переименовано в `userId`, потому что `json-server-auth`
определяет владельца ресурса именно по `userId`. Это позволило
настроить настоящую проверку прав, а не просто «пользователь вошёл».

Базовое число лайков (`recipe.likes`) и подписчиков
(`user.subscribers`) — это демонстрационные значения «сообщества».
Фактический лайк или подписка текущего пользователя хранится отдельной
записью в `likes` / `subscriptions`, а в интерфейсе значения
складываются.

## 6. API-контракт

Базовый URL: `http://localhost:3000`.

| Метод | Путь | Назначение | Доступ |
|---|---|---|---|
| POST | `/register` | Регистрация | публичный |
| POST | `/login` | Вход, возвращает `accessToken` | публичный |
| GET | `/users` | Список кулинаров | публичный |
| GET | `/users/:id` | Профиль пользователя | публичный |
| PATCH | `/users/:id` | Редактирование профиля | владелец |
| GET | `/recipes` | Список рецептов + фильтры | публичный |
| GET | `/recipes/:id` | Один рецепт | публичный |
| POST | `/recipes` | Создание рецепта | владелец |
| GET | `/comments?recipeId=` | Комментарии рецепта | публичный |
| POST | `/comments` | Добавить комментарий | владелец |
| GET | `/likes?userId=` | Лайки пользователя | публичный |
| POST / DELETE | `/likes`, `/likes/:id` | Поставить / снять лайк | владелец |
| GET | `/bookmarks?userId=` | Закладки пользователя | публичный |
| POST / DELETE | `/bookmarks`, `/bookmarks/:id` | Сохранить / убрать | владелец |
| GET | `/subscriptions?userId=` | Подписки пользователя | публичный |
| POST / DELETE | `/subscriptions`, `/subscriptions/:id` | Подписаться / отписаться | владелец |

### 6.1. Фильтрация и сортировка

Используются штатные query-параметры `json-server`:

```
GET /recipes?q=тыква
GET /recipes?dishType=Супы&difficulty=Средняя
GET /recipes?timeMinutes_lte=30
GET /recipes?ingredients_like=авокадо
GET /recipes?_sort=likes&_order=desc&_limit=6
GET /recipes?id=1&id=2
```

- `q` — полнотекстовый поиск по строковым полям;
- `_lte` — верхняя граница времени приготовления;
- `_like` — частичное совпадение, в том числе по элементам массива
  ингредиентов;
- `_sort` / `_order` — сортировка по дате, лайкам или времени;
- `_limit` — ограничение ленты на главной;
- повторяющийся `id` — выборка нескольких рецептов по списку id.

### 6.2. Примеры запросов

```bash
# Вход
curl -X POST http://localhost:3000/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"demo@recipehub.ru","password":"demo1234"}'
# → {"accessToken":"..."}

# Запрос с токеном
curl http://localhost:3000/users/1 \
  -H 'Authorization: Bearer <accessToken>'

# Создание рецепта
curl -X POST http://localhost:3000/recipes \
  -H 'Authorization: Bearer <accessToken>' \
  -H 'Content-Type: application/json' \
  -d '{"title":"Тест","userId":1,...}'
```

### 6.3. Формат ошибок

`json-server-auth` в части случаев возвращает ошибку не объектом,
а JSON-строкой:

```http
HTTP/1.1 400 Bad Request
"Email already exists"
```

Поэтому в `api.js` сообщение извлекается с учётом обоих вариантов:

```js
const message =
  (typeof data === 'string' && data) ||
  (data && (data.error || data.message)) ||
  `Ошибка запроса (${response.status})`;
```

Это позволяет показать пользователю осмысленный текст
«Пользователь с таким e-mail уже существует», а не общий
«Ошибка запроса (400)».

## 7. Авторизация и разграничение прав

### 7.1. Поток входа

1. Пользователь отправляет `POST /login` с `email` и `password`.
2. `json-server-auth` проверяет bcrypt-хэш и возвращает `accessToken` (JWT).
3. Клиент сохраняет токен:
   - в `localStorage`, если отмечен чекбокс «Запомнить меня»;
   - иначе в `sessionStorage`.
4. При загрузке любой страницы `appReady` читает токен, декодирует payload
   и запрашивает `GET /users/:id`.
5. Если токен истёк или сервер вернул `401/403/404`, токен удаляется,
   пользователь считается гостем.

JWT содержит `sub` (id пользователя) и `email`. Время жизни — 1 час.
Отдельного refresh-токена нет: при истечении требуется повторный вход.

### 7.2. Хранение токена

```js
export function getToken() {
  return localStorage.getItem(TOKEN_KEY) ||
    sessionStorage.getItem(TOKEN_KEY);
}

export function saveToken(token, remember = true) {
  clearToken();
  (remember ? localStorage : sessionStorage).setItem(TOKEN_KEY, token);
}
```

Пароль нигде на клиенте не сохраняется. В `localStorage` остаётся только
JWT, а все данные приложения живут на сервере.

### 7.3. Guards

Для всех коллекций задан режим `644`:

| Цифра | Для кого | Что означает |
|---|---|---|
| 6 | владелец | чтение + запись |
| 4 | авторизованные | чтение |
| 4 | гости | чтение |

Владелец определяется по `userId` (для `users` — по `id`).

| Запрос | Результат |
|---|---|
| `POST /recipes` без токена | `401 Unauthorized` |
| `POST /recipes` с `userId`, не равным `sub` | `403 Forbidden` |
| `PATCH /users/2` токеном пользователя 1 | `403 Forbidden` |
| `POST /recipes` со своим `userId` | `201 Created` |
| `DELETE /recipes/:id` своего рецепта | `200 OK` |
| `GET /recipes` без токена | `200 OK` |

Это проверено как вручную через `curl`, так и скриптом `npm run smoke`.

### 7.4. Скрытие паролей

Даже при чтении `GET /users` клиент не должен получать bcrypt-хэши.
В `server/index.js` переопределён `router.render`: перед отправкой ответа
из объекта рекурсивно удаляется поле `password`. Дополнительно
`store.js` санитизирует пользователей на клиенте.

## 8. Клиентский слой работы с API

### 8.1. `api.js`

Модуль инкапсулирует всю работу с сетью:

- `API_BASE_URL` — `''` при работе на порту 3000 (same origin) или
  `http://localhost:3000`;
- `ApiError` — ошибка с `status` и телом ответа;
- `request()` — единая обёртка над `fetch`: JSON, заголовки,
  `Authorization`, обработка `204`, сетевых ошибок и `AbortError`;
- `buildQuery()` — сборка query-строки, массивы превращаются
  в повторяющиеся параметры (`id=1&id=2`);
- `auth` — `login`, `register`, `getCurrentUser`, `logout`,
  сохранение и очистка токена;
- ресурсы `users`, `recipes`, `comments`, `likes`, `bookmarks`,
  `subscriptions` с методами `list/get/create/update/remove`.

Пример:

```js
export const recipes = {
  list(params = {}, options = {}) {
    return request(`/recipes${buildQuery(params)}`, options);
  },
  get(id, options = {}) {
    return request(`/recipes/${id}`, options);
  },
  create(data) {
    return request('/recipes', {
      method: 'POST', body: data, auth: true,
    });
  },
};
```

### 8.2. `store.js`

Кэш данных и синхронные селекторы:

- `users`, `recipes`, `likes`, `bookmarks`, `subscriptions`,
  `comments` (Map по `recipeId`);
- `currentUser`;
- `loadBase()` — параллельно загружает пользователей и рецепты,
  затем коллекции текущего пользователя;
- `loadUserCollections(userId)` — лайки, закладки, подписки;
- `loadComments(recipeId)` — комментарии конкретного рецепта;
- селекторы `getAllRecipes`, `getRecipeById`, `getUserName`,
  `isLiked`, `isBookmarked`, `isSubscribed` и мутации
  `upsertRecipe`, `addLike`, `removeLike` и т. д.

Благодаря кэшу шаблоны карточек остались синхронными: `recipeCardTemplate`
не делает запросов, а читает уже загруженные данные.

### 8.3. `appReady`

`main.js` экспортирует промис `appReady`, который:

1. восстанавливает сессию (`auth.getCurrentUser`);
2. сохраняет текущего пользователя в store;
3. загружает справочники и коллекции (`store.loadBase`);
4. при ошибке сети помечает API недоступным, но **не роняет страницу**.

Все страничные модули начинают работу одинаково:

```js
document.addEventListener('DOMContentLoaded', async () => {
  await appReady;
  // ...
});
```

Это устраняет гонки между модулями: к моменту рендера данные уже
в кэше, а состояние авторизации известно.

### 8.4. Фильтрация на сервере

Страница поиска формирует параметры и отправляет их на сервер:

```js
const params = {
  q: form.elements.query.value.trim(),
  dishType: form.elements.dishType.value,
  difficulty: form.elements.difficulty.value,
  timeMinutes_lte: form.elements.maxTime.value,
  ingredients_like: form.elements.ingredient.value.trim(),
  ...sortParams(form.elements.sort.value),
};
```

Живой поиск использует debounce 300 мс и `AbortController`:
при новом вводе предыдущий запрос отменяется, чтобы ответы не приходили
в неправильном порядке.

## 9. Разбор страниц и модулей

### 9.1. Главная (`index.html` + `recipes.js` + `social.js`)

- `recipes.js` запрашивает `GET /recipes?_sort=likes&_order=desc&_limit=6`
  и рендерит 6 популярных карточек.
- Блок «Популярные кулинары» больше не захардкожен: `social.js` берёт
  пользователей из кэша, сортирует по `subscribers` и рендерит топ-3.
- Кнопки подписки привязываются после рендера карточек.

### 9.2. Поиск (`search.html` + `recipes.js`)

- Справочники типов и сложности заполняются из `constants.js`.
- Запрос из адреса (`?query=...`) подставляется в поле поиска.
- Фильтрация выполняется на сервере, счётчик `aria-live` обновляется
  после каждого ответа.
- Кнопка «Сбросить» очищает форму и повторяет запрос.
- Ошибки API выводятся в область результатов, а не в консоль.

### 9.3. Страница рецепта (`recipe.html` + `recipe.js` + `social.js`)

- `recipe.js` запрашивает рецепт (`GET /recipes/:id`) и комментарии
  (`GET /comments?recipeId=`), затем рендерит заголовок, ингредиенты,
  шаги, видео и автора.
- Если рецепт не найден, показывается предупреждение
  `[data-recipe-not-found]`.
- После рендера вызывается `initRecipeSocial(recipe)` из `social.js`.
  Это важное архитектурное решение: раньше `social.js` читал
  `data-comments-list` на `DOMContentLoaded` и зависел от порядка
  подключения скриптов. Теперь порядок явный.
- Комментарии, лайк, закладка и подписка работают через API.

### 9.4. Вход и регистрация (`login.html`, `register.html` + `auth.js`)

- Клиентская валидация (e-mail, длина пароля, совпадение паролей,
  согласие с правилами) сохранена.
- После успешного входа/регистрации сохраняется JWT и происходит
  переход в личный кабинет.
- Ошибки сервера показываются в alert-блоках:
  - `401/400` при входе → «Неверный e-mail или пароль»;
  - `400` при регистрации с занятым e-mail → сообщение под полем
    и общий alert;
  - недоступный сервер → текст из `ApiError`.
- Кнопка отправки блокируется на время запроса.

### 9.5. Личный кабинет (`profile.html` + `profile.js`)

- `GET /recipes?userId=...` — публикации;
- `GET /bookmarks?userId=...` + фильтрация кэша — сохранённые;
- `GET /subscriptions?userId=...` — подписки;
- `POST /recipes` — создание рецепта из модального окна;
- `PATCH /users/:id` — редактирование имени и описания.
- После создания рецепта список публикаций перезагружается, после
  редактирования профиля обновляются шапка и имя в навигации.

### 9.6. Социальные функции (`social.js`)

- Лайк: `POST /likes` или `DELETE /likes/:id`; счётчик =
  базовое значение + лайк текущего пользователя.
- Закладка: `POST /bookmarks` / `DELETE /bookmarks/:id`.
- Подписка: `POST /subscriptions` / `DELETE /subscriptions/:id`.
- Комментарий: `POST /comments`, затем обновление кэша и списка.
- Все действия проверяют авторизацию и обрабатывают `401`.

### 9.7. Исправление модальных окон

В ходе E2E-тестирования обнаружилась особенность Bootstrap: если вызвать
`hide()` во время анимации открытия, окно остаётся видимым. `closeModal`
в `main.js` теперь проверяет `_isTransitioning` и, если переход ещё идёт,
закрывает окно по событию `shown.bs.modal`. Это делает сохранение
профиля и создание рецепта устойчивыми даже при очень быстром заполнении
формы.

## 10. Обработка ошибок, загрузки и доступность

- **Сетевые ошибки.** `fetch` оборачивается в `ApiError`; при
  недоступном сервере показывается баннер
  «Не удалось подключиться к API. Запустите `npm run api`».
- **Ошибки страниц.** `showApiError(error, container)` рендерит alert
  внутри контейнера (лента, результаты поиска, профиль), не ломая
  остальную страницу.
- **Состояния загрузки.** Контейнеры получают `aria-busy="true"`
  на время запроса; кнопки блокируются.
- **Пустые состояния.** Для отсутствия рецептов, закладок и подписок
  предусмотрены отдельные сообщения.
- **Доступность.** Сохранены семантические теги, `aria-label`,
  `aria-current`, `aria-pressed`, `aria-live`; новые счётчики и ошибки
  также используют `aria-live`/`role="status"`.
- **Безопасность.** Пароли не хранятся на клиенте, bcrypt-хэши
  вырезаются из ответов, пользовательский текст экранируется через
  `escapeHtml` перед вставкой в `innerHTML`.

## 13. Ограничения и задел на ЛР3

### Ограничения

1. JWT живёт 1 час и не обновляется; при истечении нужен повторный вход.
2. `json-server` — учебный мок, не рассчитан на конкурентную нагрузку
   и production-безопасность.
3. `db.json` изменяется при работе; для чистого состояния используется
   `npm run reset-db`.
4. Для работы нужен локальный API-сервер: размещение только статики
   (например, на GitHub Pages) не обеспечит авторизацию и данные.
5. Демо-пароли известны и предназначены только для проверки.

### Задел на ЛР3

- `api.js` — готовый слой для замены `fetch` на `axios`;
- `store.js` — прообраз хранилища состояния (Pinia/Vuex);
- `appReady` — прообраз асинхронной инициализации приложения;
- разделение на страничные модули естественно ложится на компоненты
  и composables;
- query-параметры фильтрации можно напрямую перенести в router
  (query string) и в запросы axios.
