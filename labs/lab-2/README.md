# TableBook — лабораторная работа №2

## Цель работы

Перевести сайт бронирования столиков из лабораторной №1 с локальных данных на работу с настоящим backend — моковым REST API на json-server, с авторизацией по токену.

## Что сделано

Добавлен `json-server-auth` поверх `json-server`: данные о ресторанах, пользователях и бронированиях теперь хранятся в `db.json`, а не в коде страниц. Файл `routes.json` описывает кастомные маршруты API, сервер поднимается командой `npm run server` на `http://localhost:3001` (конфигурация — в `package.json`).

Весь прежний код, который раньше читал данные из `js/data.js`, переведён на обращения к API через новый модуль `js/api.js`. Он оборачивает `fetch`: подставляет заголовок `Authorization: Bearer <токен>`, если пользователь авторизован, и приводит ошибки ответа к единому формату.

Изменения по файлам:

- `js/api.js` — новый модуль, вся работа с сервером идёт через него;
- `js/auth.js` — вход и регистрация теперь реальные запросы к `json-server-auth` (`/login`, `/register`), токен и данные пользователя сохраняются в `localStorage` через `setSession`/`getToken`/`currentUser`;
- `js/search.js`, `js/restaurant.js` — список ресторанов и карточка ресторана подгружаются с сервера вместо статичного массива;
- `js/profile.js` — бронирования читаются, создаются и отменяются через API, а не через `localStorage`, как было в лабораторной №1;
- `db.json` — хранит рестораны, пользователей и бронирования, то есть выступает базой данных на время разработки.

## Вывод

Сайт избавлен от «фейковых» клиентских данных: бронирования и пользователи теперь живут на сервере и видны одинаково из любого браузера. Это подготовило код к миграции на Vue в лабораторной №3, где структура обращений к API практически не менялась — менялся только слой отображения.
